### [개발 원칙]

1. (규칙 1 - 역할 분담 및 Thin Client):
   - 프론트엔드(HTML/JS)는 데이터 렌더링 및 사용자 입력 중계만 담당한다.
   - 모든 비즈니스 연산, 데이터 가공, 유효성 검증은 백엔드(Python) 객체가 전담하며, 인터페이스는 RESTful HTTP API(JSON)를 이용한다.

2. (규칙 2 - 명세 및 주석 표준):
   - 모든 파이썬 모듈, 클래스, 함수(메서드) 시작 부분에 한글 독스트링(Docstring)으로 목적, 매개변수(types/description), 반환값(returns)을 명확히 정의한다.
   - 복잡한 비즈니스 로직 구간 및 주요 조건 분기점에는 상세한 인라인 한글 주석을 작성한다.

3. (규칙 3 - 주 객체 중심 모듈화 및 크기 제한):
   - 모든 파이썬 소스 파일(`.py`)은 하나의 명확한 **주 객체(Main Class 1개)**를 중심으로 구성한다.
   - 해당 주 객체 내부에서만 직접 사용되는 보조 요소(전용 예외 클래스, 데이터 클래스 등)만 동일 파일에 제한적으로 포함할 수 있다.
   - 파일명은 해당 주 객체의 역할과 책임을 명확히 드러내도록 명명한다.
   - (비대화 방지): 주석 및 독스트링을 포함한 단일 파일의 전체 길이는 200줄 이내, 개별 메서드는 30줄 이내를 원칙으로 하고, 이를 초과할 경우 역할을 세분화하여 새 파일로 분리한다. 다만, 불가피하게 기준을 초과해야 하는 경우, 초과 사유를 별도 Text로 작성하고, 작업 완료 후에 사용자의 검토를 받는다.

4. (규칙 4 - UI 레이아웃 및 공통 사이드바 규격):
   - (진입분기) index.html 접속 시 스크립트로 기기(PC/모바일)를 판별하여 각 환경(모바일/PC)의 첫 화면으로 자동 이동
   - (PC 환경) 화면은 `frontend/pages/*.html` 다중 페이지로 분리하며, 좌측 사이드바와 우측 메인 콘텐츠의 2분할 레이아웃을 기본으로 한다.
      . 레이아웃 시프트(덜컹거림)를 방지하기 위해 `frontend/css/common.css`에서 좌측 사이드바 컨테이너(`<aside id="sidebar-container">`)의 너비를 고정(`width: 220px; flex-shrink: 0;`)한다.
      . 사이드바 메뉴는 `frontend/components/sidebar.html` 단일 파일로 공통 관리하며, `frontend/js/load_sidebar.js`를 통해 각 페이지의 `#sidebar-container`에 동적으로 주입한다.
      . `load_sidebar.js`는 현재 URL 경로(`window.location.pathname`)를 감지하여 해당 메뉴 링크에 `active` 클래스를 자동 부여한다.
   - (모바일 환경) 화면은 `frontend/mobile/pages/*.html` 다중 페이지로 분리하며, 상단 헤더 + 하단 탭바 네비게이션을 기본 레이아웃으로 한다
      . 공통 네비게이션(상/하단 바)을 frontend/mobile/components/nav.html 단일 파일로 분리 및 load_mobile_nav.js를 통해 동적 주입한다.
      . 모바일 터치 환경에 맞춘 m_common.css 스타일 적용한다.
   - (공통) HTML 내 CSS/JS 참조는 서버 배포 시 경로 오류를 방지하기 위해 상대경로(예: `../css/common.css`, `../js/api.js`)를 표준으로 사용한다.

5. (규칙 5 - 데이터 주도 입출력 검증 및 매개변수 완전성):
   - 소스 코드(`backend/app/.../*.py`)와 단위 테스트(`backend/tests/.../test_*.py`)는 1:1로 매칭한다.
   - 테스트용 입력값과 기대 출력값은 하드코딩하지 않고 `backend/tests/fixtures/` 폴더 아래 별도의 데이터 파일(JSON/TXT)로 분리 저장하며, 복수의 테스트 케이스 목록을 구성한다.
   - 기본값(`default`)이 존재하는 매개변수라도 테스트 데이터의 `input` 필드에는 모든 매개변수를 생략 없이 명시해야 한다. 
   - 모든 단위 테스트 코드는 실행 전 `inspect` 모듈을 활용해 대상 메서드가 요구하는 모든 파라미터가 `input`에 기재되어 있는지 자동 검증(Assert)한 뒤, `[입력값 | 예상값 | 실제 실행 결과]`를 터미널에 대조 출력한다.

6. (규칙 6 - 배치 연산, 외부 시스템 연동 및 알림):
   - 대량 데이터 처리 및 주기적 배치 연산은 `backend/app/services/batch_processor.py`의 `BatchProcessor` 클래스(비즈니스 객체)가 전담하며 웹 UI와 완전히 독립적으로 동작한다.
   - (작업 설정 형식): 배치 작업에 필요한 설정 데이터(작업 대상, 파라미터, 필터링 조건 등)는 **JSON 또는 구조화된 Text 파일**로 정의하며, `BatchProcessor`는 이 설정 파일을 읽어 작업을 실행하거나 Spark 등 외부 시스템으로부터 전달받아 처리한다.
   - (외부 인터페이스): Spark 등 외부 시스템과의 주기적 연동을 위해 백엔드에 전용 REST API 엔드포인트(`/api/batch/...`)를 제공하고 JSON 통신을 수행한다.
   - (결과 알림): 배치 작업 완료 및 에러 발생 시 처리 요약 데이터를 `backend/app/services/discord_notifier.py`의 `DiscordNotifier` 객체를 통해 사용자의 디스코드 채널로 자동 발송한다.

7. (규칙 7 - 보안 및 배포 환경 최적화):
   - 웹 프레임워크는 PythonAnywhere(WSGI) 환경과 완벽히 호환되는 Flask 기반 REST API를 사용하며, DB는 `data/app.db` (SQLite)를 표준으로 사용한다.
   - 디스코드 웹훅 URL, DB 접속 정보, Spark 통신용 API 시크릿 키 등 민감한 정보는 `.env` 파일로 격리 관리하며, `.gitignore`에 등록하여 외부에 노출되지 않도록 한다.

### [진행 및 응답 규칙]

1. (명시적 지시 전 코딩 및 실행 절대 금지):
   - 사용자가 명시적으로 **'수정해'**, **'그대로 진행해'**, **'작업시작해'**라고 지시하기 전까지는 절대로 임의로 소스 코딩을 시작하지 않는다.
   - 항상 먼저 **구체적인 구현/수정 계획(Plan)을 제시하여 사용자의 사전 승인**을 받은 후에만 코딩 단계로 진입한다.
   - 코딩이 완료된 후에는 테스트 코드를 실행하여 원하는 결과가 나오는지 확인하고 그 결과를 함께 보고한다.

2. (질의응답 및 원인 분석 시 수정 금지 원칙):
   - "~할 수 없어?"와 같은 가능성/방법 문의에는 **실제 코드를 작성하지 않고 적용 가능한 방법과 방향성만 제시**한다.
   - "왜 그렇지?", "원인 파악해", "다시 확인해봐" 등의 문제 분석 요청에는 **원인 분석 결과와 제안 수정안만 텍스트로 제시**하며, 사용자가 제안을 검토하고 선택·지시하기 전까지는 절대 코드를 직접 수정하지 않는다.
---


어떠한 경우도 명시작으로 '수정해', '그대로 진행해', '작업시작해' 라고 얘기하기 전까지는 코딩을 시작하지 마.
우선, 계획을 세우고, 내게 승인받고, 그리고 코딩을 시작해.
코딩 완료 후에도 내가 '실행해'라고 얘기하기 전까지 실행하지 마.

 
~할 수 없어? 라고 묻는다면, 방법만 제시해.
왜 그렇지? 원인파악해. 다시 확인해봐. 등을 묻는다면, 그 이유만 분석하고 수정안만 제시해. 
반영은 내가 선택하 이후에 수정을 시작해.
