# 모의투자 화면 배선 및 매수·매도 모달 개선 계획

## 1. 배경

투자제안 화면(`/proposal`, `/proposal-mobile`)은 백엔드-프론트가 완전히 배선되어 동작한다.
반면 모의투자 화면(`/recommendation`)은 다음 상태로, 사실상 정적 목업이다.

- 화면 전용 JS 컨트롤러가 없다. 로드되는 `static/js/app.js`는 메인 대시보드용이라 이 화면에서 아무 동작도 하지 않는다.
- `btnFetchRec`(당일 조회), `btnNextDayRec`(다음날 조회), `btnOpenManualBuyModal`, `btnConfirmManualBuy`, `btnResetPortfolio` 등 버튼에 이벤트 핸들러가 없다.
- 자산·보유 표, 매도 시그널 표, 추천 표가 모두 하드코딩된 샘플 행이다. `/api/recommended-stocks`, `/api/paper-trading/portfolio?account_type=rec` 를 호출하지 않는다.
- `/recommendation` 라우트는 SSR 값(`latest_trading_date`, `kospi_regime`)을 주입하지 않아 기준일·최근 수집일·모달 날짜가 하드코딩(`2026-08-19`, `2026-08-22`)으로 고정되어 있다.

즉 `account_type='rec'` 계좌와 관련 API·DB는 준비되어 있으나 화면에서 접근이 불가능하다.

추가로, 투자제안·모의투자 공통으로 **매수 모달에 총금액(단가 × 수량) 표시가 없다.** 매도 모달에는
`sellModalTotal` 표시가 있으나 매수 모달에는 대응 요소가 없어, 단가와 수량을 입력해도 총 체결금액을
확인할 수 없다.

## 2. 투자제안과 모의투자의 판단·체결 기준일 차이

투자제안과 모의투자는 "어느 날짜 정보로 신호를 판단하는가"가 서로 다르다.

### 투자제안

- 사용자는 오늘(D-0) 종가 기준으로 산출된 추천 종목을 받는다.
- 실제 매수는 사용자 입장에서 다음날(D+1) 종가에 이뤄진다. 그러나 그 시점이 되면 서버 입장에서는
  그날이 다시 D-0이므로 "신호 판단일 = 체결일"이 성립한다.
- 따라서 투자제안은 `proposal_advisor.py`의 현재 동작(기준일 지표로 신호 산출, 기준일 종가를
  추천가로 사용)을 그대로 유지한다. 변경 없음.

### 모의투자

- 사용자는 과거의 어느 날을 기준일(D-0)로 놓고, 그 "오늘 창"에서 매수·매도를 기록한다.
- 그러나 시스템은 기준일 직전 거래일(D-1) 정보로 매수·매도 신호를 판단해야 한다. 기준일 당일
  지표로 당일 체결하면 미래 정보를 당겨 쓰는 것이 되기 때문이다.
- 매매 입력값(단가·수량)의 초기값은 기준일(D-0) 종가를 기준으로 제공한다.
- 요약: 모의투자 = 판단 기준일 D-1, 체결·평가 기준일 D-0. 이는 `backtest_engine.py`의
  "D-1 신호 ➔ D-0 종가 체결" 규격 및 `recommendation.html`의 기존 안내문구와 일치한다.
- 자동 체결은 하지 않는다. "다음날 조회"로 기준일만 다음 거래일로 전진하며, 매수·매도는 사용자가
  버튼을 눌러야만 체결된다. 매도 시그널은 표시만 한다.

## 3. 요구사항 정리

1. 모의투자 화면을 투자제안과 동일한 방식으로 실제 배선한다. 계좌유형은 `rec`, 데이터 소스는
   투자제안이 쓰는 두 API(`/api/recommended-stocks`, `/api/paper-trading/portfolio`)를 쓰되,
   모의투자는 "판단 기준일 = 기준일 직전 거래일(D-1)" 모드로 호출한다.
2. 모의투자의 매수 추천 종목과 보유 종목의 전략 매도 신호는 D-1 지표로 산출한다. 추천가·보유
   평가액·손절(-5%)·익절(+10%) 판정은 D-0(기준일) 종가를 사용한다.
3. "다음날 조회"는 추천·평가 연산이 실제로 쓰는 거래일 달력(수급 일별
   데이터 `investor_trading_daily`의 거래일)을 근거로, 현재 기준일보다 큰 첫 거래일로
   기준일을 이동시킨 뒤 화면 전체를 재조회한다. 마지막 거래일에 도달하면 더 진행하지 않고 안내한다.
   주말·공휴일 건너뜀은 이 거래일 달력이 자동으로 처리한다.
   엔진의 D-1 계산도 이미 로딩된 같은 시세의 거래일 인덱스를 쓰므로 스텝과
   신호 판단이 어긋나지 않는다.
4. 매수/매도 모달의 단가 입력칸에는 기준일(D-0) 종가를 기본값으로 채워 넣고, 사용자가 편집할 수
   있게 한다.
5. 매수 시 수량(주식수)을 자동 계산해서 채워준다. 산식은 `현재 총자산 ÷ 최대 슬롯(5) ÷ 기준일 종가`
   (20% 분할)이며 잔여 현금 한도 내에서 내림한다. 수량은 사용자가 조정할 수 있다.
6. 매수·매도 모달에 총금액(단가 × 수량)을 실시간으로 표시한다. 단가/수량을 바꾸면 즉시 갱신된다.
   이 개선은 투자제안 화면에도 동일하게 반영한다.
7. 일자별 자산 이력 테이블이나 자산 곡선 차트는 만들지 않는다. 화면에는 (a) 현재 기준일 시점의
   자산평가(보유 평가액·총자산·평가손익)와 (b) 누적 최종 자산만 보이면 되고, 지속 저장은 기존
   `paper_portfolio`(현금·보유잔고·`total_asset_value`/`updated_at`) 갱신으로 충분하다.
8. `/recommendation` 라우트도 투자제안처럼 SSR 값을 주입하고, 템플릿의 하드코딩 날짜·샘플 표 행을
   제거한다.

## 4. 할 작업

### A. 투자제안·모의투자 공통 — 매수/매도 모달 총금액 표시

- 매수 모달(`manualBuyModal`)에 "총 매수 금액" 표시 요소(`buyModalTotal`)를 추가한다. 단가 또는
  수량 입력이 바뀔 때마다 `단가 × 수량`을 계산해 갱신한다. 값이 비어 있으면 `- 원`으로 표시한다.
- 매도 모달(`manualSellModal`)의 기존 총 정산 예정 금액 표시(`sellModalTotal`)는 유지한다.
- 대상 화면: PC 투자제안(`templates/proposal.html`), 모바일 투자제안(`templates/proposal_mobile.html`),
  모의투자(`templates/recommendation.html`). 공용 컨트롤러
  `static/js/proposal.js`에 총금액 갱신 로직을 넣는다.

### B. 모의투자 화면 배선 — 공용 컨트롤러 `static/js/proposal.js` 확장

- 별도 파일을 만들지 않고 `proposal.js`를 계좌 인자화한다. `recommendation.html`이
  `window.PROPOSAL_ACCOUNT="rec"`를 주입하면 컨트롤러가 D-1(sim) 모드로 동작한다(투자제안은 기본
  `prop`/advice).
- `recommendation.html`에서 대시보드용 `app.js` 로드를 제거하고 `proposal.js`(+ Chart.js CDN)를
  로드한다. 하드코딩된 샘플 표 행을 삭제하고 표 3종(자산·보유 / 매도 시그널 / 추천)을 동적 렌더로
  전환한다.
- `recommendation.html`에 투자제안 화면에만 있던 요소를 추가한다: 화면을 덮는 로딩 오버레이,
  평가 기준일 표시, 코스피 20일선 배지, 자산 요약값 바인딩 지점, 매도 모달, 차트 모달.
- 두 API를 D-1 판단 모드로 호출하고, 화면 상단에 "판단 기준일(D-1)"과 "체결·평가 기준일(D-0)"을
  함께 표기한다. 선택일이 휴장일이면 직전 거래일로 스냅됐음을 안내한다.
- 매수 모달: 추천 표에서 종목을 고르면 단가 칸에 기준일 종가를, 수량 칸에 자동 계산된 주식수를
  채운다. 단가·수량 모두 편집 가능하며, 하단에 "단가·수량 초기값은 기준일 종가 기준입니다" 안내와
  총 매수 금액을 함께 노출한다.
- "다음날 조회" 버튼(`btnNextDayRec`): 아래 C의 API로 다음 거래일을 받아 기준일 입력값을 교체하고
  화면 전체를 재조회한다. 응답이 없으면(마지막 거래일) "마지막 거래일입니다"를 인라인으로 안내한다.
  (투자제안 화면에는 이 버튼이 없어 바인딩이 무해하게 건너뛰어진다.)
- "당일 조회", "자산 초기화(1,000만원)", 차트 모달은 투자제안과 동일하게 동작한다.

### C. 다음 거래일 조회 API 추가 (`backend/app/api/routes_paper.py`)

- 입력: 기준일(`YYYY-MM-DD` 또는 `YYYYMMDD`).
- 출력: `investor_trading_daily.date` 중 입력일보다 큰 최소 거래일을
  `YYYY-MM-DD`로 반환한다. 없으면 `null`을 반환해 프론트가 마지막 거래일임을 알 수 있게 한다.
- 지수 일별 테이블(`market_indices_daily`)이 아니라 수급 일별 데이터를
  쓰는 이유: 두 테이블의 최신 거래일이 다를 수 있고(지수 데이터가 며칠 뒤처지는 경우가 있음),
  추천·보유 평가는 수급 일별 데이터를 기준으로 하므로 그쪽 거래일에 맞춰야 "다음날 조회"가
  엔진의 기준일 스냅과 어긋나지 않는다.

### D. 모의투자용 D-1 판단 모드 (`backend/app/services/proposal_advisor.py`, 두 API)

- `ProposalAdvisor`에 판단 기준일 오프셋을 두는 `mode` 파라미터를 추가한다. 기본값은 현행
  (`advice`, 오프셋 0, 투자제안용)이고, 모의투자는 `sim`(오프셋 -1)로 호출한다.
- 오프셋 -1일 때: 매수·매도 신호 행은 기준일의 직전 거래일(`_signal_date`)에서 뽑고, 추천가·종가·
  평가액은 기준일(`_eff_date`, D-0) 행에서 뽑는다. 직전 거래일은 이미 로딩된 시세의 거래일 목록에서
  인덱스로 계산한다.
- 보유 종목 매도 판정: 전략 매도 신호는 D-1 기준, 손절(-5%)·익절(+10%)은 D-0 종가와 매수가 비교로
  판정한다.
- `ProposalAdvisorCache`의 캐시 키에 `mode`를 포함시켜 투자제안(advice)과 모의투자(sim)의 결과가
  섞이지 않게 한다.
- `/api/recommended-stocks`, `/api/paper-trading/portfolio`에 `mode` 쿼리 파라미터를 받는다(미지정
  시 `advice`). 모의투자 프론트만 `mode=sim`으로 호출한다.
- 응답에 판단 기준일(`signal_date`, D-1)과 체결·평가 기준일(`eval_date`, D-0)을 함께 담아 화면이
  두 날짜를 표기할 수 있게 한다.

### E. 매수/매도 체결가·수량 처리 (`backend/app/api/routes_paper.py`)

- `manual-buy`: 단가가 오지 않으면 기준일(D-0) 종가를 DB(`InvestorTradingDaily`의 기준일 이하 최근
  거래일 종가, 투자제안 `stock-info`와 동일 소스)에서 조회해 기본 체결가로 쓴다. 사용자가 편집해
  보낸 단가가 있으면 그 값을 존중한다. 수량이 없거나 0이면 `내림(현재 총자산 ÷ 5 ÷ 종가)`로
  산정하고, 잔여 현금이 부족하면 매수 가능 수량으로 하향한다. 매수일은 실제 거래일로 스냅한다.
- `sell`: 단가가 오지 않으면 기준일 종가를 기본 매도가로 쓰고, 사용자가 편집해 보낸 값이 있으면
  존중한다. 수량은 사용자 지정값(부분 매도 허용)을 유지한다.
- 위 종가 기본값 로직은 `account_type == 'rec'` 에만 적용해 투자제안(`prop`) 계좌 동작에는 영향을
  주지 않는다.
- 기준일 종가 조회 실패(거래정지·데이터 없음)이고 사용자가 단가도 안 보냈으면 `400`으로 체결을
  거부하고 사유를 반환한다.

### F. `/recommendation` 라우트 SSR 주입 및 템플릿 정리 (`app.py`, `templates/recommendation.html`)

- 기존 헬퍼 `_latest_trading_date()`, `_kospi_regime_ssr()` 를 재사용해 `recommendation.html`에
  기준일 기본값·최근 수집일·코스피 20일선 국면을 서버 렌더 시점에 주입한다.
- 템플릿의 기준일 입력값, "최근 수집일" 텍스트, 매수 모달 날짜의 하드코딩을 SSR 값으로 치환한다.
- 코스피 20일선 배지를 투자제안과 동일한 패턴으로 추가한다.

### G. 부수 정합

- 최대 슬롯 수(5)와 화면 문구("20% 분할 매수")의 일관성을 유지한다.
- `_ymd` 파싱 실패 시 오늘 날짜로 대체하는 동작은 이번 범위에서 건드리지
  않았다(모의투자 프론트가 항상 유효한 날짜를 보내고, 잘못된 날짜여도 종가 조회 실패 시 400으로
  걸러지기 때문). 필요 시 별도로 다룬다.

## 5. UI 표현 방식

- 모의투자 레이아웃·표 3종·모달은 기존 `recommendation.html` 구조를 유지하며, 투자제안과 시각적으로
  동일 계열로 정리한다.
- 모의투자 상단 컨트롤 바에 "판단 기준일(D-1)"과 "체결·평가 기준일(D-0)"을 나란히 표기해, 사용자가
  어제 정보로 판단하고 오늘 종가로 체결한다는 흐름을 알 수 있게 한다.
- "다음날 조회" 클릭 시 별도 페이지 이동 없이 기준일 입력값이 다음 거래일로 바뀌고 표 전체가
  새로고침된다. 마지막 거래일이면 인라인 안내가 뜬다.
- 매수 모달: 단가 = 기준일 종가로 프리필(편집 가능), 수량 = 자동 계산값으로 프리필(편집 가능),
  하단에 총 매수 금액과 단가·수량 초기값 안내 문구를 함께 노출한다.
- 매도 모달: 단가 = 기준일 종가로 프리필(편집 가능), 수량 = 보유 수량 기본값(부분 매도 가능),
  하단에 총 매도 정산 예정 금액을 노출한다.
- 총금액은 단가·수량 입력이 바뀔 때마다 즉시 갱신된다.
- 조회 지연 시 투자제안과 동일하게 화면을 덮는 로딩 오버레이를 표시한다.

## 7. 검증 방법

- 모의투자 화면에서 과거 기준일 선택 → 당일 조회 → 추천 표·보유 표·자산 요약이 채워지는지 확인.
- 추천 종목이 기준일이 아니라 기준일 직전 거래일의 신호로 뽑혔는지, 추천가는 기준일(D-0) 종가인지
  확인(같은 날짜로 투자제안 화면과 대조 시 종목 구성이 하루 차이로 달라야 한다).
- 추천 종목 매수: 모달에 종가·자동 수량·총금액이 표시되고, 체결 후 현금과 보유 평가액이 산식대로
  변하는지 확인.
- "다음날 조회" 반복: 기준일이 거래일 단위로만 전진하고(주말·공휴일 건너뜀), 보유 종목 평가액과
  총자산이 각 기준일 종가로 재평가되는지 확인. 마지막 거래일에서 인라인 안내 확인.
- 매도: 단가 기본값이 기준일 종가이고 총 정산 금액·현금 반영이 맞는지, 전략 매도 신호가 D-1 기준으로
  뜨는지 확인.
- 투자제안 화면: 매수/매도 모달에 총금액이 실시간 표시되고, 기존 추천·체결 동작에 회귀가 없는지 확인.
- 규칙 5(데이터 주도 테스트)에 따라, 사용자가 "테스트 코드 작성해"라고 지시하면 D-1 판단 모드,
  다음 거래일 API, 체결 기본값 로직에 대한 단위 테스트와 fixture를 추가한다.

## 8. 구현 결과 (2026-08-28)

계획대로 구현 완료. 주요 결정·확인 사항:

- 모의투자 컨트롤러는 신규 파일 대신 `proposal.js`를 `window.PROPOSAL_ACCOUNT`
  로 계좌 인자화해 공용화. `recommendation.html`은 `proposal.js` + Chart.js CDN을 로드하고
  `PROPOSAL_ACCOUNT="rec"`를 주입한다.
- "다음날 조회"의 거래일 달력 소스를 `market_indices_daily` → `investor_trading_daily`
  로 변경(§3.3·§4.C). DB 확인 결과 지수 데이터 최신일(예: 08-21)이 수급 데이터 최신일(예: 08-27)보다
  뒤처져, 지수 달력을 쓰면 워크포워드가 조기 종료되고 엔진 스냅과 어긋나기 때문.
- smoke 검증 완료: `mode=advice`는 `eval_date==signal_date`(회귀 없음),
  `mode=sim`은 `signal_date`=D-1·`eval_date`=D-0로 종목 구성이 하루 차이. 브라우저에서 삼성전자
  자동 단가(266,000=D-0 종가)·자동 수량(7=2,000,000÷266,000 내림)·총 매수 금액(1,862,000원) 표시,
  체결 후 현금·보유 평가액 반영, 마지막 거래일에서 "마지막 거래일입니다" 안내 확인.
- 기존 unittest는 변경 전부터 13건 실패(전략 신호 truth 대조·수집기 테스트)로
  이번 변경과 무관. `proposal_advisor`/`routes_paper` 전용 테스트는 없음(규칙 5·3에 따라 별도 지시 시 작성).
- `proposal_advisor.py`가 211줄, `routes_paper.py`가 약 420줄로 규칙 3(200줄)
  초과 → `docs/size_exceptions.md`에 사유 기록.

## 9. <span style="color:red">성능 개선 A+C (2026-08-29)</span>

<span style="color:red">"당일/다음날 조회"가 기준일마다 시세 재로딩 + 8전략 지표 재계산으로 매번 느리던 문제를
개선.</span>

- <span style="color:red">**A — 넓은 창 1회 로드·계산 + 창 내 슬라이스**: `ProposalAdvisor`가 기준일 앞뒤로
  넓은 창(워밍업 135달력일 ~ 기준일+180달력일)을 1회 로드하고 8전략 지표도 1회 계산해 캐싱한다.
  기준일이 창 안이면 필터만 수행하며, 창을 벗어날 때만 재적재한다(`_covers`/`_resolve_dates`).</span>
- <span style="color:red">**C — 워밍업 버퍼 축소**: 최장 지표는 sma60(≈60거래일). 기존 200달력일 →
  135달력일(≈92거래일)로 축소해도 신호행 지표는 동일. `load_market_dataframe`에 `warmup_days`
  선택 인자 추가(기본 200, 기존 호출부 불변), ProposalAdvisor는 `warmup_days=0`으로 호출.</span>
- <span style="color:red">캐시 키를 `(기준일, mode, 데이터버전)` → `(mode, 데이터버전)`으로 축소.
  기준일 이동은 캐시된 어드바이저가 내부 창 관리로 처리.</span>
- <span style="color:red">**검증**: 2모드 × 7기준일 추천 결과가 변경 전과 **바이트 단위 동일**(스냅샷 대조).
